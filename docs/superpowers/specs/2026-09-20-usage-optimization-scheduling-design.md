# 用量優化與停止空轉：排程設計待審閱

## 已實作、可獨立上線的查詢優化

- 瀏覽器保存歷史資料的完整資料版本。5 分鐘後先以最新資料 API 核對版本；版本相同即重用歷史，版本改变仍重新下載。沒有版本的舊資料維持原本 5 分鐘期限。
- Railway 的歷史與同星分頁使用每個服務進程共用的快取。每次先向 Supabase 讀取一筆最新資料及完整歷史版本，再重用相同版本、彩種與參數的結果。同時發生的相同大型查詢合併為一次。
- 快取最多 128 筆、序列化內容 16 MiB、5 分鐘；錯誤不保存。每次回傳獨立資料，避免呼叫者修改共用內容。進程重新啟動後重新建立快取。
- 最新版本查詢不快取於後端，保留原前端 30 秒更新判定。資料庫版本會隨歷史新增、更正與刪除改變。
- 沒有更動會員資料或探索權限。探索驗證按需載入、前端進行中請求合併、歷史頁隱藏時停止更新，均沿用既有程式。

這會減少 Supabase 大型回應的傳輸；首次查詢多一次小型版本核對，不能宣稱所有資料庫 RPC 次數都下降。Railway 仍須把結果回傳給每位使用者。新期或更正目前仍重新取得所選範圍，尚未新增增量同步協定；增量協定需同時處理舊期更正與刪除，不能只補最新一期。

## 2026-09-23 首頁前端讀取策略（與 Worker 排程分離）

首頁最新開獎卡、跑馬燈與四張 Matrix 狀態卡改由同一個前端刷新 coordinator 管理，不修改下方主 Worker／Recovery 的正式排程。首頁首次進入先同步目前畫面；其後的 fallback 僅在天天樂 09:30–13:00、今彩539／大樂透／六合彩 20:30–隔日 01:00（台北時間）每 10 分鐘執行。跨午夜的 00:00–01:00 仍屬前一日晚間週期。

每次週期讀取用 `matrix_watchdog_draw_days` 的 service-role 投影取得該日實際開獎彩種，避免大樂透非開獎日與六合彩特殊日曆持續空轉。快速來源的 `preliminary` 不得完成週期；只有正式 `confirmed` 且同一期分析與 Matrix 狀態完成，狀態摘要讀取成功，並確認目前顯示的最新開獎卡已取得同日 confirmed 資料後，才標記該週期完成並取消剩餘前端 fallback。明確的 Matrix data revision 會解除完成鎖並重讀一次，以允許官方更正；普通 visibility／online 事件不會重新啟動已完成週期。
