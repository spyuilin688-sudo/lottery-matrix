# Matrix 探索／天衍共用計算架構設計

## 目的

將 Matrix 探索與天衍改為共用同一套歷史資料準備與候選規則計算，避免同一鎖定條件、同一驗證位置、同一歷史 B／C／D／E……被重複搜尋或重複計算。

本次只調整後端計算與資料流，不修改前端 UI、探索操作流程、命中規則、連準定義或天衍正式成立條件。

## 已確認的正式計算範圍

1. 自動計算只執行「本日」。
2. 自動計算只建立近十三期來源。
3. 自動計算只執行「完整範圍」。
4. 二期、七期、十三期不得各自重跑演算法；由已儲存結果的 `lockedSourceIndex` 篩選。
5. 標準範圍不得另外重跑演算法；由完整範圍結果依既有範圍條件篩選。
6. 天天樂只執行「依號碼由小到大排序」。
7. 今彩539、六合彩、大樂透執行「依號碼由小到大排序」與「依實際開獎順序排序」；實際開獎順序資料不完整時不得以順球代替。

## 共用工作單位

舊工作單位包含 `algorithmType`，因此同一來源會分別進入加減、合值、拖牌三套工作。

新工作單位固定為：

`彩種 + 號碼順序 + lockedSourceIndex + lockedPosition`

同一工作單位內一次取得：

- 鎖定來源 A。
- 相同鎖定條件的歷史 B、C、D、E……。
- 預測期距離 `predictionDistance = lockedSourceIndex + 1`。
- 完整範圍內全部合法驗證期／球位。
- 鎖定條件本身的拖牌候選規則。
- 其餘合法驗證位置的加減候選規則與合值候選規則。

不得為加減、合值、拖牌重新搜尋相同 A／B／C／D／E……。

## 歷史資料準備

每次分析版本只建立一次歷史索引，至少包含：

- 各期順球資料。
- 可用時的落球資料。
- `號碼順序 + 球位 + 號碼 -> 符合來源期索引`。
- 每一期合法號碼陣列。

相同輸入條件的歷史來源與基礎資料不得重複掃描完整歷史。

## 候選規則計算

### 拖牌

鎖定條件本身只建立拖牌候選規則。

### 加減與合值

鎖定條件本身以外的每一個合法驗證位置，只取得一次基準號碼與預測期號碼，並在同一次資料走訪中建立：

- 加減候選規則。
- 合值候選規則。

兩種演算法公式仍各自依正式規格執行，不得互相混用。

## 探索分流

共用候選資料建立後，探索才執行自己的成立判定：

- 準4+（鎖定1碼）依既定 B、C、D……共同值與停止規則。
- 準5+（鎖定2碼）依既定候選池、逐組延續、最高連準及無效版路規則。
- 鎖1與鎖2共用同一批歷史組與候選規則資料，不得為 ruleCount 1／2 重建歷史資料。
- 探索最終結果仍分別標記 `algorithmType`、`ruleCount`、`lockedSourceIndex` 等既有欄位。

## 天衍分流

天衍不得只從「探索已成立的鎖定1碼最終版路」建立候選。

依《樂彩 MATRIX｜第13章 複合版路》正式規格，天衍應直接使用同一工作單位中的候選規則資料：

1. 共用條件必須相同：彩種、號碼順序、鎖定位置、鎖定號碼、預測期距離與來源。
2. 每條複合版路固定2條成立規則。
3. 排除「同驗證球位＋同演算法」。
4. 同驗證球位＋不同演算法、不同驗證球位＋同演算法、不同驗證球位＋不同演算法均可。
5. 從 B 開始逐組驗證；兩條規則都未命中時停止。
6. 最多驗證30個已完成歷史驗證組。
7. 統計 `rule1Only`、`rule2Only`、`bothHit`。
8. 兩條規則各自必須達 `ceil(N × 30%)` 獨立命中。
9. 同時命中只算該驗證組成功1次，不列入任何一條規則的獨立貢獻。
10. 需要3條以上規則才能覆蓋時不成立。
11. 同層級多組最高連準依正式規格處理；合併預測號碼去重後超過2碼時該完整搜尋條件全部不輸出。
12. A 只用於本期預測，不計入已完成歷史連準。

天衍使用與探索相同的候選規則來源，但探索與天衍的最終成立判定彼此獨立。

## 效能表示方式

歷史命中覆蓋資料使用固定長度位元遮罩（最多30組）或等價的不可變覆蓋表示法保存，讓天衍規則配對直接計算：

- 兩條規則聯集是否連續覆蓋。
- 第一個 `bothMiss` 的位置。
- `rule1Only`、`rule2Only`、`bothHit`。

此表示方式只改變計算方法，不改變正式規則。

候選規則配對必須先依共用條件分區，並先套用「同驗證球位＋同演算法」排除與最早失敗條件，不得先建立跨搜尋條件的全域兩兩組合。

## 分批與續跑

1. Explore 仍保留可續跑的 checkpoint／chunk 機制。
2. 一個共用工作單位必須是不可分割的最小計算單位；同一工作單位內的探索與天衍共同資料不能分別重算。
3. Explore chunk 除正式探索結果外，可攜帶該批已完成的天衍正式結果與完整驗證資料。
4. Explore 全部 chunk materialize 後，Tianyan phase 只整理／發布已完成的天衍結果，不得重新搜尋歷史或重新建立候選規則。
5. Worker 中途重啟時，只允許從尚未完成的工作單位繼續；已完成 chunk 不重算。

## 儲存與查詢

### 探索

沿用 `matrix_explore_results`：

- 每條正式探索版路只存1筆。
- `item` 保存列表需要的正式結果。
- `validation` 保存展開版路需要的完整驗證資料。
- 二期／七期／十三期用 `lockedSourceIndex` 篩選。
- 標準／完整範圍由完整結果篩選。
- 同碼、預測號碼統計與列表直接對已存結果查詢。

### 天衍

沿用既有 `tianyan` analysis artifact，不新增正式資料表。

天衍 artifact 必須保存正式結果及完整歷史驗證資料，供狀態與後續正式讀取使用；不得要求前端重新計算。

### Matrix 狀態

狀態只讀取本分析版本已完成的 Explore／Tianyan／Tiangong 正式產物，不得重新執行探索或天衍演算法。

## Supabase

本次不新增資料表。

既有 `matrix_explore_results` 已包含：

- `locked_source_index`
- `algorithm_type`
- `rule_count`
- `item`
- `validation`

現有 RPC 已能以 `locked_source_index` 篩二／七／十三期，並由完整範圍結果切標準範圍。

演算法版本需從 `matrix-python-v7` 升為新版本，RPC 必須只讀取新版本，禁止新舊演算法結果混用。

## 版本與舊資料

1. 新共同計算流程使用新的 `analysis_version`。
2. 新版 RPC 只接受新版 analysis version。
3. 舊 v7 結果不得被新版正式查詢使用。
4. 不以刪除舊資料作為切換前提；舊資料可依既有 retention 清理，但不得與新版結果混用。

## UI

本次不修改任何頁面、版面、按鈕、文字或使用者流程。

探索頁既有二／七／十三期、標準／完整、版路、連準、同碼、列表及驗證展開操作維持不變；差異只在後端由「重算」改為「讀取已保存結果並篩選」。

## 驗收條件

1. 十三期與完整範圍是唯一自動計算來源。
2. 二期／七期／標準範圍不產生新的演算法工作。
3. 加減與合值不再是兩套獨立歷史掃描工作。
4. 拖牌使用同一鎖定來源資料，但只計算鎖定條件本身。
5. 鎖1與鎖2不得重建相同歷史 B／C／D／E……。
6. 天衍不得以 Explore `ruleCount == 1` 最終結果作為唯一候選來源。
7. 天衍正式規則與30組／30%限制保持不變。
8. Explore 列表、同碼、驗證展開與 Matrix 狀態全部由已保存正式結果供應。
9. 新舊 analysis version 不混用。
10. 既有前端 UI 不變。
11. 新版結果與正式演算法案例／既有可沿用驗收測試一致。
12. 測試需證明共同工作單位數不再乘上3種 algorithmType。
