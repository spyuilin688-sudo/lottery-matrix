## Findings reported and resolved during integration

1. **High confidence / important — active analysis history can silently stop at a server row cap.** `services/matrix-api/app/repositories/analysis_repository.py`, `SupabaseAnalysisRepository._list_draw_rows`, stops when the returned page is shorter than `DRAW_PAGE_SIZE` (1000). A database cap of 100 with more than 100 matching draws returns only 100 as the complete history. Active callers include `services/analysis_pipeline.py` full-history analysis input, `services/draw_refresh.py` validation/repair, and `analysis_worker.py`. This is not dormant legacy code. Preserve ordering and advance by the actual returned count until an empty page or independently proven end; preserve explicit caller limits.
2. **High confidence / important — installed-client history compatibility route has the same truncation.** `services/matrix-api/app/api_server.py`, `_history`, stops on a short requested page. The live `/api/matrix/history/<lottery>` route still dispatches here when `pageSize` is absent. The newer `matrix_draw_query` RPC route does not make this legacy caller dormant. Fix retrieval without removing compatibility or changing draw/algorithm semantics.
3. **High confidence / moderate — recent-history query has no continuation.** `SupabaseAnalysisRepository.list_draws_since` performs one select. Its active caller, `DrawRefreshService._recent_history`, requests the last 31 calendar days. Expected daily rows fit the default cap, but a cap below the result count hides history. Use stable ordered continuation while retaining the date predicate. Do not rewrite stored draws.
4. **High confidence / moderate — chunk retrieval assumes the requested page size.** `SupabaseAnalysisRepository._iter_artifact_chunks` stops when fewer than `ARTIFACT_CHUNK_PAGE_SIZE` (2) chunks arrive. A cap of 1 prevents reading a valid multi-chunk artifact. Materialization/summarization checks validate totals, so this fails loudly rather than silently publishing a partial artifact. Continue using the last actual `chunk_index` and retain the non-progress check.
5. **High confidence / important — notification member/subscription reads silently truncate under a lower database cap.** `apps/admin/backend/push-notifications.ts`, `listAllRows`, requests Range pages of 1000 and ends on any short page. `listMemberPushStatus` uses it for all members and enabled subscriptions. A cap of 100 with 150 rows hides later members; incomplete subscription rows can falsely mark a returned member as having push disabled. Advance by the actual count and prove completion instead of treating a short page as the end. The Auth users endpoint is a separate pagination contract.
6. **Specification question reported — subscription member list sorting controls.** The backend supports whitelisted sort/date queries, but the active `SubscriptionManager`/`useAdminMemberPage` interface initially exposed keyword and plan filters only. Final inspection confirms both member and subscription screens now use `AdminListControls` and the shared server-page hook for date/sort queries. The subscription disabled filter was also checked against the final backend: its explicit disabled branch precedes the default active group and retains plan/expiry eligibility.

7. **High confidence / important — the active manual-transfer screen accepts an obsolete read.** `src/features/MemberPages.tsx`, `ManualTransferPage`, starts `fetchPendingTransferRequest()` in an effect depending on `onNavigate` and `plan`, without cleanup or generation checking. The production `Prototype` recreates `onNavigate` on renders. Start read A, rerender with a new callback to start B, resolve B with a pending transfer, then resolve A with `null`: A clears the newer pending record and re-enables submission. This is a live route through `features/router.tsx`, not the patched legacy history/TongXing paths. The PWA implementer added the focused reproduction/fix, including the same screen's session ownership; final disposition is recorded below.
8. **High confidence / important — active subscription/referral reads do not invalidate on account change.** `useSubscriptionProfile()` cancels only on unmount; `InviteFriendsPage` increments revisions for refresh/unmount but subscribes to no authentication change. Production routes are not keyed by member identity. A late account-A profile/referral read can become the visible account-B result, or an already-visible A result can persist. `memberRpc` returns a successful response without its own session-result fence. The coordinator authorized the PWA implementer to address these concrete ownership gaps.

9. **High confidence / critical — authentication recovery can replay an old member write under a new account.** `src/member-api.ts`, `memberRpc`, receives the original RPC's `PGRST301`, validates the current user with `auth.getUser()`, then repeats the captured RPC/arguments without checking its original session generation. If account A changes to B between the first request and recovery, A's notification settings or transfer arguments can be resubmitted under B. A late definitive-invalid `getUser` response can likewise sign out the current account. UI completion guards cannot stop these newly issued recovery mutations. Preserve legitimate same-session recovery but fence recovery, sign-out and replay by the original owner. The coordinator authorized the PWA implementer to fix this and add deferred auth-recovery regressions.

## Distinctions and limitations

- The notification delivery-log UI explicitly says “latest N records,” and its endpoint intentionally returns the latest 200. This was disclosed to the coordinator as a recent-feed limit, not confused with an undocumented full-history result. The user requirement determines whether historical notification log navigation must also be added.
- `list_job_statuses` has four known job rows and `list_progress_for_periods` has three analysis candidates. These are naturally bounded inputs that fit the normal database cap; caps below those bounds still deserve consideration, but differ from unbounded history truncation.
- `SupabaseCardRepository._list_all` uses the Storage listing API's requested 100 items. It is not subject to the PostgREST `db-max-rows` setting; no independent evidence established a lower Storage cap.
- Optional geolocation enrichment degrades to a missing region without discarding the main member/login row. Visitor-stat failures are represented as `null` and displayed as “—”, rather than fabricated zero. These are explicitly degraded fields, not successful empty replacements for primary records.
- The reliability fixes reviewed here do not rewrite stored data or alter algorithm rules. Separately imported upstream-main changes are outside that claim. No claims about deployment configuration, production response limits, full browser layout equivalence, or all PWA/CI/CSS changes are made by this reviewer.
